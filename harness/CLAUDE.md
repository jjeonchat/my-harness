# 허들링 디자인 하네스

## 목적과 실행 위치

사용자 흐름 1개를 대상으로 레퍼런스 수집·분석, 화면 설계,
키스크린 제작, 컨셉 승인, 디자인 확장, 검토를 수행한다.

Claude Code는 이 파일이 있는 harness/ 폴더에서 실행한다.
이 문서의 경로는 별도 표시가 없으면 harness/ 기준이다.

## 시작 전 읽을 문서

판정 기준:
- ../prd.md
- ../story-service.md
- ../design.md

실제 작업 과정:
- ../story-workflow.md

서비스 목적과 실제 작업 경험을 혼합하지 않는다.
문서에 없는 요구사항이나 사용자의 경험을 만들어내지 않는다.

상세 실행 계약:
- harness-R2-purpose.md: 목적과 완료 기준
- harness-R3-pipeline.md: 단계별 입출력과 복귀 경로
- harness-R4-artifacts.md: 파일명과 재개 방식
- harness-R5-gates.md: 승인된 판정 조건
- harness-R6-roles.md: 역할과 편집 경계
- harness-R7-orchestrator.md: 실행 조정과 기록 권한
- harness-R8-validation.md: 검증 사례와 리뷰 기준

디자인 원문의 충돌은 R5에서 승인한 해석을 적용한다.
추가 충돌이나 미정 사항은 임의로 결정하지 않는다.

## 실행용 규칙

스크립트가 읽는 판정 규칙의 단일 기준은 rules.json이다.
각 규칙은 ID, 판정 대상, 조건, 원문 근거를 포함한다.

기준 문서와 rules.json은 실행 중 읽기 전용이다.
규칙이나 필수 판정 수단이 준비되지 않았다면
검사를 수행한 것처럼 기록하거나 통과 처리하지 않는다.

## 실행 단위와 기록

실행마다 runs/<실행ID>/를 사용한다.
서로 다른 실행의 파일을 덮어쓰지 않는다.

- input.json: 대상 흐름, 화면 목록, 제공한 레퍼런스
- run-state.json: 단계 상태, 입력·규칙·산출물 해시, 재시도 횟수

단계별 산출물 경로는 R4를 그대로 따른다.
디자인은 Figma에 두고, 대응 파일에 노드 링크와
검사에 필요한 구조화 데이터를 기록한다.

## 역할과 편집 권한

다음 경로는 해당 실행 폴더 기준이다.

- 리서처: 01-research/만 편집
- 화면 설계자: 02-spec/만 편집
- 컨셉 디자이너: 03-concept/만 편집
  - approval.json은 편집 금지
- 디자인 확장자: 04-design/만 편집
- 판정자: 읽기 전용, 결과·근거·복귀 단계만 반환

Figma에서도 컨셉용·확장용 영역을 구분한다.
작업자는 자신의 영역만 수정한다.

오케스트레이터가 직접 기록할 수 있는 범위:
- input.json
- run-state.json
- 03-concept/approval.json
- 05-review/ 안의 결과 파일

오케스트레이터는 작업물을 대신 수정하지 않는다.
판정 결과를 임의로 통과로 바꾸거나 사람 승인을 대신하지 않는다.

## 실행 순서

1. 레퍼런스 수집·분석
2. 화면 설계
3. 키스크린 제작 및 컨셉 승인
4. 디자인 토큰·컴포넌트·전체 화면 제작
5. 최종 검토

동시에 실행하는 작업자는 최대 1개다.
각 단계 완료 시 산출물과 해당 단계의 필수 조건을 확인한다.
미통과 또는 판정 불가가 있으면 다음 단계로 넘어가지 않는다.

사용자가 제공한 URL 또는 캡처에서 레퍼런스 수집을 시작한다.
접근 불가 자료를 기록하고, 분석 가능한 자료가 0개이면 중단한다.

## 컨셉 승인

사람 승인 지점은 3단계 한 곳이다.
사용자가 내부 관계자와 협의한 최종 결과를 입력한다.

승인은 실행ID와 컨셉 버전에 연결한다.
승인 누락 또는 변경 전 컨셉의 승인으로 4단계를 진행하지 않는다.
컨셉 변경 시 같은 지점에서 재승인받는다.
“계속해”만으로 승인 기록을 만들지 않는다.

## 필수 게이트

R5의 조건을 판정하며, 증거 누락·조회 실패는
판정 불가로 기록하고 진행을 막는다.

기본 검사:
- 키스크린 2~3개
- 키스크린 모두 390×844
- 합의한 화면 목록 대비 누락 0개
- 승인된 디자인 규칙 위반 0개

관련 기능이 포함된 실행의 서비스 검사:
- 자산의 기본 공개 범위는 private
- 사용자 선택 없는 공개·판매 신청 전이 0개
- seller 이외 역할의 판매 신청 허용 0개
- 운영자 검수 없는 승인 전이 0개
- MVP의 판매 중·판매 중지 상태 0개

관련 없는 항목은 근거와 함께 해당 없음으로 기록한다.
해당 없음을 통과로 집계하지 않는다.
설계의 권한 검사를 실제 서버 접근 제어 검증으로 표현하지 않는다.

## 복귀와 재개

컨셉의 시각 표현 문제는 3단계로 복귀한다.
화면 구성·기능 누락이나 화면 설계 자체의 누락은 2단계로 복귀한다.
최종 검토의 토큰·컴포넌트·화면 표현 위반은 4단계로 복귀한다.
수정 후 5단계를 재실행한다.

자동 수정은 검사 항목별 연속 2회까지다.
계속 실패하면 원인을 기록하고 중단한다.
재개 요청만으로 재시도 횟수를 초기화하지 않는다.

재개 시 입력·규칙·산출물 해시를 확인한다.
변경이 없고 완료된 단계만 건너뛴다.
변경된 단계와 그 이후 단계는 다시 수행한다.

## 검증과 리뷰

첫 검증 흐름은 “내 자산 등록 → 판매 신청”이다.
가상 검증 데이터와 실제 작업 자료를 구분한다.

R8의 정상·위반·중단·재개 사례를 모두 검증한다.
검증용 데이터로 판정 스크립트를 검사하고,
실제 Figma 노드에서도 크기·스타일·누락을 확인한다.

보고서에 다음을 기록한다:
검사 ID, 예상 결과, 실제 결과, 증거, 실패 원인, 복귀 단계.

검증 완료 조건:
- 필수 테스트의 예상·실제 불일치 0건
- 필수 테스트의 미실행·판정 불가 0건
- 미해결 필수 위반 0건

실행하지 않은 검사를 통과했다고 기록하지 않는다.
위반 사례가 기대대로 차단된 테스트 성공과
실제 디자인 작업의 완료를 구분한다.

## 자연어 트리거

- “[흐름명] 디자인 시작”
- “[실행ID] 이어서 진행”
- “[실행ID] 컨셉 [버전] 승인”
- “[실행ID] 검토”

대상 실행이나 승인 버전이 불명확하면 확인한다.

## 디자인 작업 완료 기준

화면 설계서, 키스크린, 디자인 토큰·컴포넌트,
합의한 전체 화면 디자인이 존재하고,
현재 컨셉 버전의 유효한 승인 기록 1건이 있으며,
적용되는 필수 검사가 모두 통과해야 완료다.

## 구현 사용법

실행 명령과 데이터 계약은 README.md와 schemas.md를 읽는다.
`sh scripts/harness --help`로 지원 명령을 확인한다.
작업자 호출 전 `begin`, 반환 후 `finish`로 단계를 전환한다.
승인은 사용자의 위 형식 메시지를 `approve --message`에 그대로 전달한다.
판정자는 `check` 결과를 읽기만 하고, 오케스트레이터가 `review`로 저장한다.
등록되지 않은 명령이나 존재하지 않는 도구를 실행했다고 보고하지 않는다.
